## Concrete authority boundaries inspected

API resource authentication (`auth.ts`, runtime composition in `external-booking-api/index.ts`) verifies actual JOSE signatures, administrator-pinned issuer/resource/JWKS, `at+jwt`, approved asymmetric algorithms/client IDs, bounded `iat`/`nbf`/`exp`, required scope and current provider introspection on each request. Outages fail closed. Tenant customer resolution joins the verified issuer/subject and requested operator; body email/customer IDs and operator-owner records do not establish a renter. API tokens do not establish BFF customer authorization by themselves. Introspection must contain the requested action even when a formerly issued JWT still lists broader scopes.

Direct ingress must use the configured public HTTPS origin. Supabase-origin ingress requires a short-lived HMAC over exact method/path/query/body before normalization. Arbitrary forwarded Host/IP headers are not authority. Frontend BFF reconstructs the public URL only when Host exactly matches the configured authority; POST additionally requires exact Origin and session CSRF. An internal Request.url does not select public authority. Deployed ingress stripping/signing and DNS/egress protections remain unproven locally.

Managed customer OIDC login uses PKCE/state/nonce/issuer binding and fresh `auth_time`; encrypted purpose-bound AES-GCM `__Host` Secure/HttpOnly/SameSite cookies hold a short session and no refresh token. Cookie and bridge keys must differ. Backend customer routes require a separately signed30second proof over method/path/body/access-token hash, verified issuer/subject/client and CSRF hash in addition to managed bearer introspection. Verified OIDC email alone, from that signed profile proof, can link an operator customer after an explicit customer click; typed email and agent-supplied ownership selectors are rejected/stripped. Legacy guest identity is not silently reused: external eligibility requires an owned prior request and verification after the verified link.

Quotes/consent/request SQL (`0901`, `0904`, `090470`, `0906`) binds immutable pricing/terms/window/options/hash to issuer/subject/original agent client/customer/operator/audience. Fresh hosted consent stores precisely customer-selected action scopes; identity is not an implicit default. Requests lock quote and receipt before their ledger foreign keys, recompute authority, consume once, and atomically create booking/grant/outbox/immutable response. Same-key replay returns its durable response before quote expiry or new-write admission; changed identity/payload is a conflict, withdrawn delegation denies replay, and retries cannot create another booking. Replay intentionally returns the original creation representation rather than claiming current confirmation.

Grant and handoff operations revalidate current ownership/link/revocation/expiry in the authoritative transaction. Renewal preserves original client/scopes/booking; revoked IDs stay revoked, fresh authorization creates another ID, and hold/payment deadlines are not extended. Request-bound proof is separate from agent authority. Customer-owned account continuation uses its independently verified customer session/current tenant link and does not add an agent grant or scope. Agent nonces require the original action-specific grant, while customer-session nonces require current owner authority independently. Nonce recovery creates only an explicit pending renewal; completing it requires another fresh customer review/consent. Nonce IDs/booking refs/grant IDs are selectors, not bearer authority.

Provider handoffs use hashed10minute opaque nonces, booking-first lease/state checks, immutable provider attempt start/key, durable session references and short internal endpoint/body/time HMACs. Source internal context requires an actual current claim token in SQL; a service JWT or caller boolean alone cannot create an external lease. Rental checkout shares one booking reservation across source and external callers; incompatible flow/origin and ambiguous old attempts fail closed. Exact HTTPS action-specific Stripe hosts, no userinfo/non443 ports, credential/receipt query rejection and bounded Checkout-only documented `#fidkd` are enforced by the shared canonical format. Browser-only provider URLs are never persisted in new SQL or returned to agents. Generic first-party returns contain public ref/action only, and customer pages do not interpret redirects as payment success.

Signed provider events or trusted SDK retrieval establish settlement evidence; reference-only rows, redirects or caller totals do not. Payment proof checks succeeded intent, exact amount/received/currency/mode/booking/leg/operator destination; SQL checks immutable consented financial/rental tuple and requires both exact legs plus current identity for confirmation. Duplicate/out-of-order events and stable fee attempts are fenced; partial/uncertain money remains recoverable. Migration090730 now retains issued/ambiguous checkout inventory regardless of missing webhook, and protects reservation metadata and DELETE. This safely closes late-webhook inventory release; it deliberately does not clear unpaid expired sessions automatically. Existing raw exception logging in webhook signature/handler branches still warrants owner/hosting redaction review; this audit did not demonstrate a particular secret leak from those logs.

Inventory guards cover booking INSERT/UPDATE/DELETE and blocked-date INSERT/UPDATE/DELETE with sorted old/new vehicle try-locks, both BEFORE and AFTER checks, blocking membership and snapshotted post-return buffers. Noninventory metadata updates avoid unnecessary lock errors; later BEFORE-trigger changes are still checked by the AFTER guard. Availability/quote/write share half-open semantics. UNKNOWN authority fails closed in adapters, direct booking facade and mounted Dates/Review flows, including captured handlers and changed/stale windows. Full deployed writer/caller retry compatibility remains a gate even after selected real local PostgreSQL races pass.

New activity is disabled by default and denied on configuration outage. Transaction triggers independently gate quote/receipt/request insertion, so a flag change after HTTP preflight cannot admit a write. Existing authenticated owner status, replay, grant recovery and customer handoff continuity survive admission rollback. Global rollout requires a privately reviewed admin binding plus current verified source user/admin; source email fallback or an editable super-admin row alone is insufficient. Service/browser roles cannot seed the independent binding or directly mutate protected flags. Operator opt-in uses current source team-owner/admin membership, whose applied RLS integrity must still be reviewed in staging. Required request/settlement/confirmation audit records are transactional; optional telemetry copies only bounded redacted enums/UUIDs/hashes/timings and cannot undo a committed request.

MCP resource tokens are distinct from API tokens. Actual resource verification/introspection and provider token exchange preserve issuer/subject/original consumer client and narrow scopes; API authority is verified again on every API call. Tool schemas expose no approval/card/document-upload authority. Submission obtains receipts through the authenticated server rendezvous; awaiting202 performs no booking write, and altered hints do not substitute for a receipt. Process-local rate/inflight budgets and fixed remote destinations exist; the formerly unbounded POST body is now bounded locally, while deployment distributed limits remain a gate.
