# Independent MCP preparation review

Reviewed adapter-worktree commit3236034ed6c66c0c923224d520c63fb84af52148, actual src/tests/contracts and mcp-compatibility notes. Static read-only review; no package edits, tests, hosted browser acceptance or live calls. Three concrete findings follow. Paths below are relative to packages/renter-mcp unless marked shared.

1. **Medium — status tool is advertised read-only/idempotent but creates renewal records.** src/server.ts:27 marks get_request_status readOnly:true/idempotent:true. src/api-client.ts:42,45–47 catches grant_expired/grant_revoked and POSTs grant-renewals, a persistent consequential operation requiring customer reauthorization. Reproduction: call get_request_status with an owned expired/revoked grant; return the structured grant error from GET; observe POST /v1/rental-requests/{ref}/grant-renewals. Even if backend reuses a pending renewal, it still creates one on first read. Fix: separate explicit recovery operation or mark status readOnly:false; retain idempotent:true only if backend proves keyed/stable renewal reuse. Add actual tools/list+expired/revoked call regression, not merely happy-path status tests.

2. **Medium — inbound disconnect is not propagated to authentication/API egress.** src/node-http.ts:16 constructs Request without a disconnect AbortSignal; src/server.ts:59–61, src/auth.ts:56–66 and src/api-client.ts:17 never connect inbound cancellation to boundedJson. http.ts:3,6 replaces any supplied signal with its own timeout controller. Reproduction: issue a tool POST, let body finish, stall metadata/API fixture and close client socket before result; provider exchanges/API calls continue until their individual deadlines, and a later request POST can still begin after client is gone. Existing runtime test covers response-stream disconnect at node-http.ts:18, not in-flight provider/API cancellation. Fix: pass a controller aborted on premature res.close/request abort through auth/SDK/API operations and compose it with per-call deadline; check before subsequent network steps. Test disconnect during metadata, consent-result and before request POST (no new POST after cancellation), while documenting unavoidable already-committed ledger replay.

3. **Medium — customer URL projection trusts generic HTTPS contract instead of exact customer route policy; encoded secret query keys bypass generic denylist.** src/api-client.ts:28–29 forwards validated QuoteResult/CheckoutHandoffResult/RentalStatusResult unchanged; quote/checkout handlers at34/43 do not apply the origin/path/query guard used for renewal54. Shared supabase/functions/_shared/external-booking/contracts.ts:109–110 tests raw URL.search with a token-key regex. Reproduction: a schema-valid checkout result whose customer_url is https://attacker.example/agent/handoff/x is returned to tool output; a URL https://customer.example/agent/handoff/x?%74oken=legacy-secret also passes the raw token regex because URL.search retains percent encoding. The same issue applies to scoped links/quote consent URL. Fix: apply configured customer origin and exact owned route checks to all customer-facing links, decode search parameter names before secret rejection, preferably reject all query parameters on owned consent/handoff routes. Require configured API-origin/path policy for status links. Add contract-valid wrong-origin and percent-encoded-key response tests. This is adapter defense/privacy enforcement; it does not claim the pending hosted implementation actually emits unsafe URLs.

Positive evidence: incoming/exchanged asymmetric JWTs bind fixed issuer, exact distinct audiences, subject, original registered client_id and scope subset; fresh introspection checks active+identity+audience+jti/expiry; per-tool scope is selected before dispatch and JSON batches refused. Credential destinations are pinned HTTPS issuer-origin endpoints; redirects refused, byte/time/concurrency limits and safe errors are present. Receipt is obtained through consent-result and used only server-to-server; schemas reject receipt/grant tool input/output. Legacy and modern transport tests use official SDK clients; this review did not rerun them. No concrete original-client token substitution or per-tool scope bypass was found.

Release gate remains separate: package preparation depends on completed09/14 handoff integration, actual provider original-client token exchange and PKCE, customer browser consent/recovery/replay, distributed gateway limiter, API flags/ACL parity, identity/payment sandbox and settled-leg acceptance. Local protocol fixtures are not hosted acceptance. The findings above concern prepared package code and should be fixed before claiming release readiness; no deployment approval is implied.
