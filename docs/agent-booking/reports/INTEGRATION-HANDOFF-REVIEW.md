### Previously residual P1 — Delayed payment webhook versus inventory expiry

At reviewed backend `244039d1`, customer payment can complete through an already issued Checkout session just before `payment_due_at`. If its webhook arrives after the scheduler run, the database can still have null `paid_at`, no payment-intent refs and no settlement record. `rent-payment-scheduler/index.ts:144-148` reconciles database lifecycle state and invokes `expire_overdue_payment_bookings`; it does not retrieve/expire the stored Checkout session. `20261007090500_external_lifecycle_reconciliation.sql:229-232` preserves inventory only for database financial evidence, not `rental_checkout_session_ref`. Inventory can therefore be released before the late paid event is recorded.

The31-minute creation floor and frozen provider expiry alone cannot prevent paying an existing session immediately before its deadline. Final090730 (`4e95ed1f`, plus DELETE hardening `fc656387`/`796f542e`) enforces the safe side of the invariant: any issued or ambiguous checkout keeps inventory, regardless of missing webhook or elapsed timer. Reservation metadata cannot be cleared, and BEFORE DELETE blocks a legacy reserved booking without depending on an external-ledger FK. Unreserved legacy deletion remains compatible. Scheduler queues a bounded fair SKIP LOCKED manual-review batch before expiry and refuses expiry on queue failure. Source-inspected implementation and independently rerun scheduler checks close the unsafe release defect locally; owner-reported actual PostgreSQL race evidence is separately labeled below.

This is conservative retention, not an automatic provider-authoritative expiry worker or safe manual-clearance RPC. Neither cleanup path is implemented. Inventory may remain held indefinitely pending a reviewed operations procedure. Older pre-migration legacy provider sessions lack reservation metadata and require audit/drain/reconciliation at rollout. These mandatory gates prevent a production acceptance claim; no timer or absent webhook is treated as unpaid proof.

## Findings

### P1 — Real checkout return URLs are rejected by the actual customer page

Backend `supabase/functions/rent-checkout/index.ts:203` and `:204` append `&payment=success` / `&payment=cancelled` to the external return base. `provider-handoff.ts:40` requires those same three-field URLs. Frontend `domain/booking/customerProviderReturn.ts:8` accepts precisely two fields (`booking_ref`, `action`); `hostedAuth.server.ts:21` also rejects the extra field in owned login destinations.

Trigger: any successful/cancelled external hosted Checkout return. Result: `Invalid provider return`, with no current customer status or preserved sign-in flow. Synthetic browser tests used the two-field return and therefore did not exercise the real provider-generated URL. External success/cancel should use the exact generic owned return; retain legacy semantics separately and verify the literal URLs from actual source handler parameters through the frontend parser/login.

### P1 — Fragment rejection conflicts with Stripe's documented Checkout response

Backend `handoff-store.ts:15`, canonical `contracts.ts:116`, and generated browser validation reject all URL fragments. Stripe's [official Checkout create reference](https://docs.stripe.com/api/checkout/sessions/create?api-version=2025-08-27.basil) includes a returned `checkout.stripe.com/c/pay/...#fidkd...` URL. Therefore the documented provider response is rejected by the current code. This is primary-source compatibility evidence, not a claim that real sandbox responses were exercised.

Source checkout validates the URL before persisting `rental_checkout_session_ref` (`rent-checkout/index.ts:213-214`), so this failure can leave a created Stripe session behind an ambiguous reservation. Repeating with the durable idempotency key returns the same provider object and fails again. Review the action-specific provider fragment policy using actual Stripe test responses; never silently discard a provider fragment or weaken generic first-party URL validation. Exact Stripe host/protocol and browser-only disclosure still apply.

### P2 — Newly implemented nonce grant recovery has no frontend entry point

Backend `handoff-routes.ts:27-34` exposes explicit customer `POST /v1/customer-handoffs/{nonce}/grant-renewals` and SQL `:455-466` binds it to the original grant/client/scopes. Frontend `customerHandoffServer.ts:18` collapses all errors, including `grant_expired` / `grant_revoked`, to `handoff_unavailable`; SSR handoff page `:15` discards non-200 results; hosted proxy allowlist `:8` excludes this path. The landing offers retry/ask-agent only.

Trigger: customer possesses an agent-created nonce whose original delegation expired or was revoked. They cannot enter the newly provided explicit renewal flow from that nonce. Existing customer-account continuity works if they separately retained the account link. Preserve only the two safe backend recovery codes, add an explicit CSRF-bound renewal action with canonical `GrantRenewalResult` and an exact first-party authorization URL, and never renew automatically.

### P2 — Customer-owned nonce creation upgrades a shared booking lock

`external_create_customer_owned_handoff` calls `external_customer_rental_status` (`SQL:439`), which takes `FOR SHARE OF b0,link` (`:413`), before acquiring `FOR UPDATE` on the same booking (`:440`). Two concurrent customer-create transactions can both hold a shared booking lock and each wait to upgrade. The 500ms lock timeout bounds the wait and yields a retry, but this differs from the booking-first exclusive ordering already used by claim/provider/complete paths.

Use an ownership lookup that does not first acquire a shared booking lock, or obtain the exclusive booking lock in a consistent order before performing the current linked-customer checks. A real two-connection test should prove one succeeds/one receives bounded retry with no deadlock-shaped upgrade; this review did not mutate the SQL lab.

### P1 — Hosted Checkout can still accept payment after backend expiry releases inventory

`rent-checkout/index.ts:170-211` does not set Stripe `expires_at`. [Stripe's official create reference](https://docs.stripe.com/api/checkout/sessions/create?api-version=2025-08-27.basil) documents default24-hour lifetime and a configurable30-minute-to24-hour creation window. `provider-handoff.ts:40` requires only provider expiry in the future, without binding it to `booking.payment_due_at`.

Trigger: customer opens Checkout shortly before an earlier backend deadline (`min(approval+48h,pickup-2h)`), then pays after that deadline. Source `expire_overdue_payment_bookings` (`20260725045744_fa25b9ea-3209-4ab2-bade-3d1744f0b5b2.sql:60-68`) can mark the unpaid booking expired. The new financial hold guard (`20261007090500_external_lifecycle_reconciliation.sql:229-230`) checks PI/paid/settlement evidence, not an open `rental_checkout_session_ref`. No `checkout.sessions.expire` call exists in the checked function tree. Thus an already issued provider URL can outlive the released inventory. Late settlement then requires financial reconciliation and cannot safely assume that inventory remains available.

This is a code-based race inference supported by documented provider lifetime, not a real payment reproduction. Bind session expiry to the approved deadline where Stripe permits; for near-deadline windows and concurrently completing sessions, expire/retrieve/reconcile the provider session before releasing inventory. Test the provider-paid-vs-expiry race using the actual existing settlement and inventory guards.

### P2 — Identity nonce rotation resets the age of an unchanged provider idempotency key

SQL `:85` /`:446` reject an ambiguous provider attempt only when `old.created_at+23h` has passed. Rotation copies `provider_attempt_key` and `provider_recorded_at` but sets the new row's `created_at` to `moment` (`:88` /`:449`). Repeated rotation within23hours preserves the original provider key while resetting the age gate indefinitely. `provider-handoff.ts:24` retries identity creation with that inherited key when no session reference was recorded.

If creation succeeded but durable recording repeatedly remained ambiguous, rotations can eventually reuse a key older than Stripe's retention window. [Stripe documents](https://docs.stripe.com/api/idempotent_requests) that a pruned key produces a new request after at least24hours. Checkout has a separate immutable booking reservation timestamp; identity lacks one. Preserve an immutable original provider-attempt start timestamp across nonce rotation and fail closed into reconciliation after the safe retry window. A recorded session can still be retrieved under current authority; do not reset an ambiguous key automatically.

## Operational limitations observed

- Shared checkout reservation (`SQL:337-340`) safely prevents a legacy and external flow from creating independent operator charges, but permanently rejects a different flow kind/origin for that booking. If a legacy email link wins the initial reservation, an otherwise authorized external customer continuation is blocked. This is intentional fail-closed financial protection rather than a security bypass; an operational reconciliation/recovery path and clear customer guidance are still needed.
- Claim expiry is bounded at2minutes; source provider fetch is bounded8seconds and browser bridge5seconds. A bridge timeout can leave a valid lease busy until it expires. Provider idempotency/session-reference retrieval protects retried creation, but customer errors currently say generic retry and do not expose the real remaining busy interval. No unbounded database wait was found in claim/provider/complete SQL.
- Nonce is consumed before returning the provider URL. A dropped HTTP response after completion cannot replay the consumed nonce; recovery needs a newly created customer/agent nonce that inherits the durable provider reference. The customer account path supplies that explicit creation flow.
- Final explicit nonce grant recovery now supplies the previously missing path for safe grant_expired/grant_revoked codes; it creates a pending original-client/scopes review only after a customer click and does not authorize automatically. A dropped successful provider response still requires a new nonce/customer account continuation.
- Automatic provider expiry/retrieval cleanup and safe manual hold clearance are absent. Immutable issued/ambiguous reservations therefore keep occupancy until a reviewed operations recovery exists; pre-migration legacy session drain is independently mandatory.

Verified internal provider error branches log constant messages; handoff API/browser DTOs exclude legacy credentials/session references. First-party account links carry a safe public ref only.
