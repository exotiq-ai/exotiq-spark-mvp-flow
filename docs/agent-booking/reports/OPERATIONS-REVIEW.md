## Controls verified

The shared JWT key resolver now has request-local pre/post abort gates. Production-factory tests establish both disconnect after introspection and disconnect while an availability body finishes before key resolution; neither starts subsequent protected work. An in-flight shared key fetch is intentionally not cancelled for another principal, remains bounded by JOSE's three-second timeout and uses the pinned issuer URL. These checks do not prove deployed connection cancellation or undo a remote write already started. Supabase destinations, source edge paths and managed endpoints are administrator pinned; private DNS/rebinding prevention remains a deployment gate.

**Bounded source ingress:** `source-body.ts` enforces one total five-second read deadline, immediate inbound abort, bounded accumulated bytes and cancellation without awaiting an untrusted producer. Actual identity-create-session and rent-checkout use64KiB strict object/UTF-8 input before admin/provider work. The helper's lower test deadline proves the same budget mechanism; hosted transport acceptance still must demonstrate runtime cancellation behavior.

**Managed JWKS byte limit:** JOSE6.2.3's shared resolver uses its own fetch and `response.json()`; this code sets a three-second timeout, but does not add a body byte/key-count ceiling. A pinned trusted issuer can still return a large key set within that window. Do not claim that the API/source ingress byte limits also cover JWKS. Require the selected issuer's bounded key-set profile/egress response limit in managed acceptance, or add a reviewed JOSE `customFetch` response cap without defeating shared rotation/cache behavior. This remaining resource-limit gap is explicitly distinct from the fixed post-disconnect fetch-start bug.
