# External booking API and renter MCP

This is an isolated implementation. Hosted OAuth, Stripe, identity, complete Supabase schema/privilege parity and market/provider acceptance remain release gates. The original backend and storefront repositories were read only. No production deployment is authorized by this document.

The API is the stable boundary. MCP calls the same API and canonical schemas. Backend table/function changes normally require adapting the server facade while preserving v1 behavior. Changing public fields, scopes or lifecycle semantics requires an explicit contract review, regenerated OpenAPI/browser validators, adapter compatibility tests and a version/migration decision. `generate-contract.mjs --check`, consumer source hashes and actual route tests detect drift; they do not automatically rewrite business logic.

## Customer journey

1. Discover opted-in, eligible operators and vehicles. Live Miami/Tampa scope is distinct from intentional demo fleet/prices and future markets. Listings never promise availability, approval or driver eligibility.
2. Check the exact offset-bearing pickup/return instants and operator time zone. AVAILABLE is a checked observation, UNAVAILABLE is a denial and UNKNOWN is an unresolved read. UNKNOWN never becomes an empty available calendar. The buffer revision and observation time accompany known results.
3. Authenticate through the separately configured managed OAuth issuer. Token signature, exact issuer/resource audience, original client, current introspection, scope and persistent API rate budget are checked on each request. Operator customer links derive from explicitly consented verified OIDC identity, never caller email or customer IDs.
4. Create an immutable, principal-bound quote (default15 minutes), including itemized integer cents, two separate charge legs, rental/protection/state/tax details, cancellation, pickup, deposit and mileage terms. A quote creates no inventory hold. A changed quote or terms requires a fresh review; clients cannot supply prices.
5. Customer opens consent_url and signs in on the hosted customer page. The browser shows that exact quote and records explicit request authorization. The customer separately selects status, identity handoff and checkout handoff permissions; the initial choices are unchecked. This permits an agent to submit that request; it approves no operator decision and authorizes no agent payment.
6. MCP submit uses only quote_id and a required Idempotency-Key. The adapter retrieves the one-use receipt through authenticated server rendezvous. Waiting is202 with bounded Retry-After and creates no booking. Receipts never enter tool input/output. The API locks receipt/quote/inventory and atomically writes one pending request, grant, ledger and notification outbox.
7. Poll the owned request. Pending_documents asks the customer to verify identity; requested/pending await the operator. Pending_payment permits customer checkout only after approval, valid identity and a live payment window. A browser return, success message or operator payment alone cannot confirm a rental. Only verified identity plus both exact settled charge legs yields confirmed.
8. Customer-only opaque handoffs use a short-lived scoped nonce, stored hashed. Browser review is read only; explicit Continue resolves a current owned action to the pinned Stripe host. Agent sees only the customer landing URL. Legacy confirmation credentials, card data and identity files stay outside the public API/MCP.

The returned `links.customer_account` is a fixed first-party page for the same request. A freshly authenticated customer can complete its own identity or payment steps there even when the agent was not delegated those actions. This customer authority does not expand or revive an agent grant.

## Retry and recovery

Generate a16–128 character ASCII Idempotency-Key before submitting. After a timeout or lost response, retain exactly that key and quote/receipt intent. Ledger-first replay returns the original request with200, even after original quote/receipt expiry. A fresh request returns201. Different payload/key reuse produces idempotency_conflict or consent denial; never blindly retry the legacy unkeyed writer. A busy inventory/request lock returns a bounded retry indication, not an assumed booking.

Status reads recheck ownership and current grants before ETag/304. Honor Retry-After/poll_after_seconds; no unbounded polling. Genuine owners receive grant_expired/grant_revoked with fixed recovery links; other owners receive the same404 as a missing ref. Ref-based renewal preserves25h/71h holds and the original client/scopes. Customer reauthenticates and explicitly authorizes stored delegation. Revoked IDs never revive; a new delegation obtains a new ID. OAuth sessions and booking grants have different lifetimes.

Identity events use atomic completion so failure can retry. Payment events record exact intent, mode, account, currency, amount and booking/leg binding. Partial payment stays in reconciliation and must not start another operator charge. Stable captured-payment attempts survive distinct webhook event IDs. Past the provider dedupe window, uncertain charges move to controlled reconciliation instead of minting a new charge key. Terminal late payments queue refund/reconciliation; provider failures do not become acknowledged success.

Quotes and requests default disabled until independent global rollout approval and per-operator opt-in. Disabling new external writes does not cancel accepted rentals or disable their status, renewal, identity, checkout and reconciliation. Persisted transaction checks protect writes against flag races. Catalog opt-out must not strand an already accepted renter.

## Contract and deployment

The generated [OpenAPI](openapi.yaml) is JSON (valid YAML1.2), OpenAPI3.1.2/JSON Schema2020-12. Its OAuth .invalid URLs are documentation placeholders; this API does not implement an issuer. Configure the actual reviewed issuer, authorization/token/introspection/JWKS endpoints, client registrations, API resource (including mounting prefix), distinct MCP resource and frontend origin. Never infer them from token claims or request Host.

Run backend `node scripts/agent-booking/generate-contract.mjs --check` and `npm run test:agent:contract -- --run`. Generate the browser schema using `node scripts/generate-external-contracts.mjs <reviewed-backend-contracts.ts>` in the isolated frontend and run its `--check` form. The browser copy records the full canonical source SHA256. MCP imports that same source and validates DTOs rather than keeping another pricing/state engine.

Backend table/function refactors can retain the existing v1 interface: update the backend mapping and migrations, then rerun authority, ownership, request replay, payment and compatibility checks. The API and MCP do not need rebuilding from scratch. A change to public fields, states, permissions or semantics requires a reviewed canonical contract update and consumer verification; an incompatible change requires a separate version/migration plan. The current CI gates generated docs/examples and offline API safety/contract tests. During a coordinated two-repository release, run `node scripts/agent-booking/check-consumer-contracts.mjs /absolute/frontend-checkout` in the backend: it compares the complete browser validator and full source hash, catching stale copies or local validator edits. MCP compilation/protocol tests consume the canonical source directly. This does not replace applied migration, hosted provider or operator acceptance checks.

See [staging gates](staging-runbook.md), [security evidence](security-review.md), [MCP compatibility](mcp-compatibility.md) and [rollout/rollback](rollout.md). Current primary protocol references: [MCP2026-07-28 authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [official SDK](https://github.com/modelcontextprotocol/typescript-sdk), [OpenAPI3.1.2](https://spec.openapis.org/oas/v3.1.2.html), [JSON Schema validation](https://json-schema.org/draft/2020-12/json-schema-validation).

Operator websites/widgets, delegated agent payment, ACP and UCP remain deferred. No universal client/provider onboarding, authority, ranking, rental eligibility or approval guarantee is made.
